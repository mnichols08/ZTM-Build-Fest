# Kin v1.0 Compatibility and Upgrade Commitment

Kin keeps years of household records, so v1.0 makes a written promise about
what later releases will keep working. This document is that promise. It
freezes every persistent and wire format at its v1.0 version, says what v1.x
releases may and may not do to each, and says what happens to data from the
v0.x pre-releases.

A CI test (`scripts/v1-compatibility.test.mjs`) reads the frozen versions
below and compares them with the constants in the code. A pull request that
changes a frozen version fails CI unless it updates this document in the same
change.

## The promise for every v1.x release

For each format below, every v1.x release will:

1. **Read everything v1.0 wrote.** Data, exports and synced events made by
   v1.0 keep opening in every v1.x release.
2. **Migrate forward without loss.** When a v1.x release needs a newer local
   format, it upgrades the data in place, journalled so an interrupted upgrade
   resumes or rolls back. It never discards a household event: canonical
   event bytes are kept exactly as written.
3. **Never drop events silently.** An event a release can't apply is kept and
   reported (see the quarantine in [SYNC](SYNC.md)), never thrown away.
4. **Add, not replace.** New capabilities arrive as new event kinds, new
   optional fields or new protocol versions that older data doesn't need.
   Devices on different v1.x releases in one household keep syncing; a device
   that receives something newer than it understands pauses sync with an
   explanation instead of guessing.

What a v1.x release **may** do: add event kinds, raise the replay protocol to
add behaviour for new events, add IndexedDB stores or server tables with a
forward migration, and add new export package formats as long as it still
reads the v1.0 one.

## What only a major version (v2.0) may change

A major version may stop reading a v1.0 format, remove an event kind, or
change the meaning of existing events. If it does:

- the release notes and the app say so before anyone upgrades;
- the last v1.x release gains (or already has) an export that the new version
  reads, and the app asks people to export first;
- the threat model and this document are updated in the same release.

It holds each format's current version: a v1.x addition that the promise
above allows, such as a server table, raises it here and is listed under
[Additions since v1.0](#additions-since-v10).


The WASM ABI (exported functions and buffer ownership) is frozen as documented
in [ABI](ABI.md): v1.x may add exports but won't change or remove the v1.0
ones.

## Additions since v1.0

Each v1.x addition keeps every frozen version above unchanged.

| Release | Addition | Older v1.x devices |
| --- | --- | --- |
| v1.1.0 | Server schema 11: tables `push_subscriptions` (one Web Push subscription per device) and `push_vapid_keys` (the service's VAPID key pair), with a forward migration from 10; routes under `/api/push/` ([PUSH](PUSH.md)). | Older clients never subscribe. A v1.0 server refuses a schema-11 database. |
| v1.1.0 | Server schema 10: tables `household_install_identity` and `household_install_identity_revisions` for an admin's published home-screen name and icons, with a forward migration from 9; the routes `/api/household/install-identity`, a per-device `/manifest.webmanifest` and `/install-icon/*` ([HOUSEHOLD-IDENTITY-DEFAULTS](HOUSEHOLD-IDENTITY-DEFAULTS.md#published-install-identity)). Encrypted household settings are unchanged. | A v1.0 server refuses to open a schema-10 database (it fails closed rather than guess); keep a backup from before the upgrade if you might roll the server back. Clients of any v1.x version are unaffected: the manifest is just a web page resource. |
| After v1.1.0 | The existing encrypted household-settings v1 JSON gains an optional `brand` member containing either the generated-letter choice or a bounded 512-pixel PNG. Missing `brand` remains valid and resolves to the generated-letter choice; no server or IndexedDB schema changes. | Older v1.x clients ignore the additional authenticated JSON member when reading it. If an older admin saves household defaults, the optional brand is omitted and newer clients safely return to the generated-letter icon. |
| v1.1.0 | Event kinds 42 `DEVICE_DESCRIBED` and 43 `DEVICE_NICKNAMED` (schema 1, replay protocol still 24); WASM export `kin_device_names` and its KDEV v1 result; KCMD actions 42 and 43 ([ABI](ABI.md), [EVENTS](EVENTS.md#v110-device-names)). The server keeps only automatic device names and resets other stored labels to "Device" at start, as data inside the existing schema 9 ([IDENTITY](IDENTITY.md#device-names)). | This happens automatically: each v1.1 device records its name after its next sync, and a v1.0 device that receives that event pauses sync with an "unsupported" error and keeps its data. It resumes once it runs v1.1, which the installed app normally picks up when it is next opened; a v1.0 tab left open stays paused until it is reloaded. A v1.0 device also can't import an export from a v1.1 household. |

## Upgrading from v0.x

The v0.x releases were pre-releases, and their formats changed often. **v1.0
makes no compatibility promise for data created before v1.0.** Start fresh at
v1.0: create a new household and pair devices again. Kin may still open some
v0.x exports and local data, but that is not guaranteed, not tested as a
supported path, and may stop in any v1.x release.

The v1.0 promise above starts with the first data written by v1.0.
